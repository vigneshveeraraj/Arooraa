# MESA demo-request reference numbers (synthetic, not persisted)

## What exists today

`ProjectEnquiry` has a real, stored, generated `enquiry_number` column (`ARO-2026-000001`
style). `DemoRequest` (MESA) does not — Milestone 1 never added one, and Milestone 2C
deliberately did not add one either, to avoid touching the already-tested MESA write path
this late without a concrete need.

Instead, the admin UI computes a **synthetic** reference on read, purely from the lead's
existing UUID:

```java
// AdminLeadQueryService.syntheticMesaReference
"MESA-" + id.toString().replace("-", "").substring(0, 8).toUpperCase(Locale.ROOT)
```

For example, id `1a2b3c4d-5e6f-4789-9abc-def012345678` always displays as `MESA-1A2B3C4D`.

## Guarantees this does and does not provide

- **Stable for a given id:** yes. This is a pure function of the UUID — nothing stateful,
  nothing random, nothing that depends on when or how many times it's computed. The same
  MESA lead will show the same reference the first time it's viewed and the millionth
  time. Covered directly by `AdminLeadQueryServiceTest.syntheticMesaReferenceIsStableForTheSameId`.
- **Not a persisted database business identifier:** correct — it is never written to any
  column, never generated by a sequence, and does not exist anywhere except as a display
  string computed at request time from `demo_requests.id`. If the underlying id-generation
  scheme for `DemoRequest` ever changed, or the row were ever exported/reimported with a
  new id, the displayed reference would change with it. It must never be treated as a
  durable external identifier (e.g. never put it in an invoice, contract, or anything that
  needs to survive independently of the database row).
- **Not guaranteed globally unique:** it's derived from only the first 8 hex characters of
  a UUID. A UUID collision on just that prefix is astronomically unlikely at MESA's actual
  lead volume, but it is not cryptographically guaranteed the way a real generated
  reference number (with a uniqueness constraint) would be. This is an accepted, documented
  trade-off, not an oversight.

## Search behaviour

The admin leads list search box matches MESA leads two ways simultaneously:

1. The normal text fields — contact name, restaurant name, email, phone — same as any
   other search term.
2. The lead's own id: if the search term starts with `mesa-` (case-insensitive), that
   prefix is stripped and the remainder is matched as a case-insensitive substring against
   the lead's UUID text. So searching `MESA-1A2B3C4D` (exactly what's shown in the UI) finds
   the lead whose id starts with `1a2b3c4d`, without that prefix ever being stored anywhere
   — see `DemoRequestRepository.search` and its `idPattern` parameter.

Searching the raw UUID itself (with or without dashes) also works, since it goes through
the same substring match. Searching a *project enquiry's* `ARO-2026-######` reference
number works too, but through the normal stored-column path — `enquiry_number` is a real
column, not a synthetic one.

## When to revisit this

If MESA ever needs a real, durable, externally-referenceable reference number (e.g. to put
on an invoice or a customer-facing communication), add a proper generated
`reference_number` column to `demo_requests` via a new Flyway migration, following the same
pattern already used for `project_enquiries.enquiry_number`. That is a deliberate, scoped
follow-up — not something this milestone changes, per its own explicit instruction not to
introduce unnecessary schema risk immediately before a first production deployment.
